# Правила разработки

Документ обязателен для всех, кто вносит изменения в репозиторий. Если правило мешает — обсуждаем и меняем документ, а не нарушаем молча.

## Структура проекта

Проект разбит на модули с чёткими границами ответственности:

| Пакет | Модуль | Что делает |
|---|---|---|
| `ocr/` | M1 | предобработка фото, OCR-движки, проверка читаемости, тестовый набор |
| `extract/` | M2 | извлечение структуры чека из текста |
| `categorize/`, `reports/` | M3 | категоризация позиций, кэш, отчёты |
| `bot/`, `pipeline/`, `storage/` | M4 | Telegram-бот, сборка пайплайна, хранилище |
| `common/` | общий | контракты между модулями (`OcrResult`, `Receipt`, `Item`, `StorageInterface`, `MonthlyReport`) |
| `dataset/` | общий | фото чеков, эталоны, размеченные данные |

Правила границ:

- Модули общаются только через контракты из `common/`. Импортировать внутренности чужого модуля нельзя.
- Изменение контракта в `common/` — отдельный PR, согласованный с владельцем контракта и всеми, кто его использует.
- Доступ к БД есть только у `storage/`. Остальные работают через `StorageInterface`.
- Модуль не делает чужую работу: OCR не разбирает поля, извлечение не ставит категории, бот не знает, как устроен классификатор.

## Python

### Окружение и инструменты

- Python 3.12+.
- Зависимости и окружение — через `uv` (`pyproject.toml` + `uv.lock`). Лок-файл коммитится.
- Линтер и форматтер — `ruff` (`ruff check`, `ruff format`).
- Проверка типов — `mypy` в строгом режиме для `common/` и публичных интерфейсов модулей.
- Тесты — `pytest`.
- После клонирования окружение настраивается командой `make setup`.
- Перед пушем обязательно выполнить `make check`: проверка форматирования, Ruff, mypy и pytest
  должны пройти.
- Для применения форматирования используется `make format`.

### Стиль кода

- PEP 8, длина строки 100, форматирование только через `ruff format`.
- Аннотации типов у всех публичных функций, методов и атрибутов классов.
- Публичные классы, функции и методы документируются Google-style docstring'ами.
- Аргументы публичных API описываются в секции `Args:`, а значимые возвращаемые значения —
  в секции `Returns:`.
- Публичные поля Pydantic-моделей и классов данных описываются в секции `Attributes:`
  docstring'а класса.
- Типы задаются аннотациями Python и не дублируются без необходимости в тексте docstring'ов.
- Приватным вспомогательным функциям docstring не требуется, если назначение ясно из имени и
  аннотаций.
- Данные между модулями — Pydantic-модели, внутри модуля — `dataclass` или Pydantic. Словари с «магическими» ключами не передаём.
- Интерфейсы (`OcrEngine`, `Classifier`, `StorageInterface`) описываем через `typing.Protocol` или `abc.ABC`; конкретная реализация выбирается конфигом.
- Имена: `snake_case` для функций и переменных, `PascalCase` для классов, `UPPER_CASE` для констант. Имена говорящие, без сокращений вроде `rcpt`, `tmp2`.
- Функции короткие и делают одно дело. Никаких побочных эффектов при импорте модуля.
- Не глотаем исключения: `except Exception: pass` запрещён. Для ожидаемых ошибок — свои классы исключений (например, `ReceiptUnreadable`), которые пайплайн превращает в понятный ответ пользователю.
- Логирование через `logging`, не через `print`. Персональные данные и содержимое чеков целиком в логи не пишем.
- Деньги храним в `Decimal` (или в копейках как `int`), не во `float`.
- Даты и время — timezone-aware `datetime`.

### Конфигурация и секреты

- Настройки — через переменные окружения и `pydantic-settings`. Шаблон — `.env.example` в репозитории.
- Токены, ключи API и `.env` в репозиторий не попадают никогда. Случайно закоммиченный секрет считается скомпрометированным и перевыпускается.
- Выбор OCR-движка, классификатора и провайдера модели — через конфиг, без правки кода.

### Тесты и качество

- Новая логика приходит вместе с тестами. Исправление бага — вместе с тестом, который его воспроизводит.
- Юнит-тесты не ходят во внешние сервисы: модели, API и Telegram подменяются заглушками.
- Тесты, требующие реальных моделей или сети, помечаются `@pytest.mark.slow` и в обычный прогон не входят.
- Скрипты оценки (`eval_*.py`) работают на общем наборе из `dataset/` и выводят воспроизводимые метрики.
- Тестовые данные и эталоны не правим «под результат». Изменения в `dataset/` — отдельный PR с объяснением.

### Зависимости

- Новая зависимость добавляется осознанно и упоминается в описании PR: зачем она нужна и почему не хватает стандартной библиотеки или уже подключённых пакетов.
- Тяжёлые зависимости (модели, OCR-движки) — в отдельной группе, чтобы бот и тесты можно было запускать без них.

## Git

### Ветки

- `main` — всегда рабочая. Прямые пуши в `main` запрещены, только через PR.
- Одна задача — одна ветка. Ветка создаётся от свежего `main`.
- Формат имени: `<type>/<module>-<short-description>`, латиницей, через дефис.
  - `feat/ocr-easyocr-engine`
  - `fix/extract-total-validation`
  - `refactor/storage-repository`
  - `docs/readme-setup`
- Перед PR ветка подтягивается к актуальному `main` через `rebase`.
- После мержа ветка удаляется.

### Коммиты

Сообщения коммитов — **только на английском**, **в одну строку**, по [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <description>
```

- `type` — один из:
  - `feat` — новая функциональность;
  - `fix` — исправление ошибки;
  - `refactor` — изменение кода без изменения поведения;
  - `test` — тесты;
  - `docs` — документация;
  - `chore` — инфраструктура, зависимости, конфиги;
  - `perf` — производительность;
  - `data` — изменения в `dataset/` и размеченных данных.
- `scope` — модуль: `ocr`, `extract`, `categorize`, `reports`, `bot`, `pipeline`, `storage`, `common`, `dataset`. Для изменений всего проекта scope можно опустить.
- `description` — в повелительном наклонении, с маленькой буквы, без точки в конце, до 72 символов.

Примеры:

```
feat(ocr): add EasyOCR engine behind OcrEngine interface
fix(extract): retry when model returns invalid JSON
test(categorize): cover cache hit and miss paths
chore: configure ruff and mypy
```

Правила:

- Один коммит — одно логическое изменение. Не смешиваем рефакторинг, фичу и форматирование.
- Коммит не ломает сборку и тесты.
- Никаких `wip`, `fix`, `update`, `asdf` в качестве сообщения.
- Не коммитим сгенерированные файлы, артефакты сборки, настройки IDE, большие бинарники вне `dataset/`.

### Pull Request

- Заголовок PR оформляется так же, как сообщение коммита.
- В описании: что сделано, зачем, как проверить. Если задача из плана — ссылка на неё.
- PR небольшой: ориентир — до 400 строк изменений без учёта данных и лок-файлов.
- Нужен минимум один аппрув от другого участника. Изменения в `common/` — аппрув от владельцев затронутых контрактов.
- Мерж — `squash`, итоговое сообщение по тем же правилам коммитов.
- Замечания ревью либо исправляются, либо обсуждаются в треде. Резолвит тред автор замечания.

## Чек-лист перед PR

- [ ] Ветка актуальна относительно `main`.
- [ ] `make check` проходит (проверка форматирования, Ruff, mypy и pytest).
- [ ] Новая логика покрыта тестами.
- [ ] Контракты в `common/` не менялись или изменение согласовано.
- [ ] Нет секретов, отладочного кода и закомментированных кусков.
- [ ] Сообщения коммитов на английском, в одну строку, по формату.
