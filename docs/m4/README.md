# M4: ход разработки

Зона ответственности: Telegram-бот (`bot/`), пайплайн (`pipeline/`) и хранилище (`storage/`).

Здесь по итерациям записано, что было сделано в M4 и почему. Итерация — это период, за который накопилась серия моих коммитов.

## Итерация 1. Старт проекта (28–29.09)

Коммиты:

- `docs: add project readme and contributing guidelines`
- `docs: add module overview and architecture diagram`

Сделано:

- README с описанием идеи и CONTRIBUTING с правилами кода, веток и коммитов.
- Разделение системы на модули M1–M4 и схема архитектуры (`docs/architecture.jpg`, `docs/architecture.pdf`).

Почему: до начала разработки нужно было договориться, кто за что отвечает и как модули передают данные друг другу.

## Итерация 2. Бот как отдельный компонент (03.10)

Коммиты:

- `chore: set up uv project with ruff, mypy and pytest`
- `feat(bot): add telegram bot with start, help, month and photo handlers`
- `test(bot): cover start, month and photo handlers`
- `feat(bot): reply in russian or english based on telegram language`
- `test(bot): cover language detection and middleware`
- `docs(bot): describe telegram bot module in readme`

Сделано:

- Бот на aiogram 3: `/start`, `/help`, `/month` и приём фото.
- Бот обращается к остальной системе через интерфейс `ReceiptService`. Остальных модулей ещё не было, поэтому вместо них стояла заглушка с готовым текстом ответа.
- Ответы на русском или английском: язык берётся из `language_code`, который Telegram присылает с каждым сообщением. Тексты собраны в `bot/texts.py`.
- Тесты обработчиков без обращения к Telegram.

Вход: сообщения Telegram (команды, фото). Выход: текст ответа пользователю.

Открытые вопросы:

- Сервис возвращал боту готовую строку. Из-за этого ответы заглушки были только на русском, а бот не мог сам оформить результат.

## Итерация 3. Соединение с M2 и хранилище (11.10)

Коммиты:

- `feat(pipeline): parse receipt photos and reply with store, date and total`
- `feat(storage): save receipts and show monthly spending`

Сделано:

- Пайплайн (`pipeline/receipt.py`) вызывает этапы по очереди: распознавание текста, разбор чека через `extract.parse_receipt` (M2), сохранение.
- Если на чеке нет ни даты, ни суммы, пайплайн выбрасывает `ReceiptUnreadable`, и бот просит переснять фото.
- Хранилище чеков на SQLite (`storage/receipts.py`).
- `/month` считает сумму и число чеков за текущий месяц. Границы месяца берутся в часовом поясе пользователя, а не в UTC.

Было: сервис возвращал боту строку.
Стало: сервис возвращает `Receipt`, а бот сам оформляет ответ на нужном языке.
Почему: оформление ответа относится к боту, а пайплайн должен отдавать данные. Так исчезла проблема с ответами только на русском.

OCR ещё не был готов, поэтому на месте M1 стояла заглушка, и любое фото считалось нераспознанным.

Открытые вопросы:

- В `common/` два разных `Receipt`: один отдаёт M2, другой ждёт M3. Пока их не сведут в один контракт, классификатор нельзя подключить к пайплайну.
- Интерфейс хранилища лежит в `storage/`, хотя по CONTRIBUTING контракты должны быть в `common/`.
- Повторно присланный чек сохранялся и учитывался дважды.

## Итерация 4. Соединение с M1, повторы и история (18.10)

Коммиты:

- `feat(pipeline): recognize receipts with configured ocr engine`
- `feat(bot): accept receipt images sent as files`
- `feat(storage): skip duplicate receipts`
- `feat(bot): add history command with recent receipts`
- `feat(bot): add undo command to delete last receipt`

Сделано:

- Заглушка OCR заменена на `OcrService` из M1, движок выбирается переменной `OCR_ENGINE`. Теперь цепочка фото, текст, чек, сохранение работает целиком.
- Ошибки OCR разделены. Битое изображение считается нераспознанным чеком, и пользователь получает просьбу переснять. Недоступный движок считается сбоем сервера и пишется в лог.
- Чек можно прислать файлом: Telegram его не сжимает, и OCR работает точнее. Пока идёт распознавание, бот показывает статус «печатает…».
- Повторный чек (тот же магазин, дата и сумма) не сохраняется. Существующая база обновляется при запуске без потери данных.
- `/history` показывает последние 5 чеков.
- `/undo` удаляет последний сохранённый чек и показывает, какой именно. Удаляется чек, присланный последним, а не чек с самой поздней датой.

Почему: после появления OCR в M1 можно было впервые собрать весь путь от фото до ответа. Повторы, история и `/undo` нужны, чтобы `/month` показывал правильную сумму: пользователь видит, что именно сохранилось, и может убрать чек, в котором OCR ошибся.

Открытые вопросы:

- Повтор определяется по магазину, дате и сумме. Если OCR прочитает одно из полей по-разному на двух фото одного чека, повтор не найдётся.
- `/undo` удаляет чек целиком. Исправить отдельное поле (например, сумму) пока нельзя, можно только удалить чек и прислать фото заново.
- Распознавание идёт в потоке внутри процесса бота. Непонятно, как это поведёт себя при нескольких пользователях одновременно и не стоит ли вынести OCR в отдельный сервис.
- Подключение классификатора M3 всё ещё ждёт общего контракта `Receipt` и извлечения товаров в M2.

## Итерация 5. Товары из M2 и замечания ревью (21–25.10)

Коммиты:

- `fix(bot): ignore other modules variables in shared env file`
- `fix(ocr): ignore other modules variables in shared env file`
- `feat(pipeline): parse receipt items from ocr layout`
- `fix(pipeline): report ocr engine failures as temporary unavailability`
- `test(pipeline): cover month boundaries across timezones`

Сделано:

- При первом локальном запуске всего проекта бот и OCR падали на общем `.env`: настройки каждого модуля отказывались читать чужие переменные. Теперь лишние переменные пропускаются.
- M2 научился разбирать товарные позиции по координатам блоков OCR (`extract.parse_ocr_result`). Пайплайн перешёл на этот разбор, и бот показывает в ответе список покупок.
- Сбой самого движка OCR пайплайн переводит в `RecognitionUnavailable`. Бот отвечает, что распознавание временно недоступно, а подробности остаются в логе. Раньше пользователь видел общее «не получилось обработать чек».
- Тесты на границы месяца с настоящим SQLite: переход года, смена летнего времени в Берлине, часовой пояс Владивостока и чек без даты, присланный сразу после полуночи. Проверено, что тесты падают, если месяц считать в UTC.

Было: пайплайн объявлял свой интерфейс `TextRecognizer` с методом `recognize(image) -> str`, а тесты M1 импортировали его, чтобы проверить совместимость.
Стало: пайплайн зависит от общего контракта `OcrEngine` из `common/ocr.py` и вызывает `recognize_blocks`, который отдаёт текст вместе с координатами.
Почему: координаты нужны M2, чтобы связать название товара с его ценой в строке. Кроме того, M1 зависел от внутреннего интерфейса M4, хотя по правилам модули договариваются только через `common/`.

Замечания ревью:

- Сообщение о временной ошибке OCR: сделано.
- Тест на границу месяца и часовой пояс: сделано.
- Показывать пользователю, какой чек удалён: уже было сделано в итерации 4, `/undo` выводит магазин, дату и сумму.
- Подтверждение или отмена при подозрении на повтор: пока не сделано.

Открытые вопросы:

- Как дать пользователю подтвердить повтор. Кнопке в Telegram нужно знать, о каком чеке речь, а сам чек в данные кнопки не помещается (лимит 64 байта). Его придётся где-то хранить до ответа пользователя.
- M3 всё ещё не подключён: товары теперь есть, но классификатор ждёт другой `Receipt` из `common/models.py`.
- M2 сверяет сумму позиций с итогом и пишет предупреждение `items_total_mismatch`. Бот пока его не показывает, хотя это хороший повод предложить `/undo`.

## Итерация 6. Подтверждение повторов и обратная связь пользователю (27.10)

Коммиты:

- `fix(bot): reject image files too large to download`
- `feat(bot): warn when receipt items do not add up to total`
- `feat(pipeline): log processing time of each step`
- `feat(bot): let user confirm or drop suspected duplicate receipt`

Сделано:

- Файлы больше 20 МБ бот не скачивает и сразу просит прислать изображение поменьше. Bot API такие файлы ботам не отдаёт, и раньше пользователь получал общее сообщение о сбое.
- Если сумма покупок не сходится с итогом (предупреждение `items_total_mismatch` от M2), бот пишет об этом и предлагает `/undo`. Отдельный тест сверяет строку предупреждения с константой M2, чтобы переименование в M2 не сломало проверку незаметно.
- Для каждого чека в лог пишется время распознавания, разбора и сохранения. Это первый шаг к ответу на вопрос о нагрузке из итерации 4: теперь видно, какой шаг занимает время.
- Подозрительный повтор больше не отбрасывается молча. Бот спрашивает кнопками «Сохранить ещё раз» или «Не сохранять». После ответа вопрос заменяется результатом, и кнопки нельзя нажать дважды.

Было: повтор определялся по магазину, дате и сумме, и такой чек просто не сохранялся.
Стало: решение принимает пользователь, а система только предупреждает.
Почему: замечание ревью. Две одинаковые покупки в один день дают одинаковые магазин, дату и сумму, и раньше вторая терялась без возможности её сохранить.

Как устроено подтверждение: чек не помещается в данные кнопки (лимит 64 байта), поэтому пайплайн держит в памяти последний отклонённый чек каждого пользователя. Подтверждённый повтор сохраняется без отпечатка, поэтому он не мешает следующим чекам.

Открытые вопросы:

- Ожидающий ответа чек хранится в памяти процесса. После перезапуска бот просит прислать фото заново, а при нескольких копиях бота кнопка может попасть не в тот процесс. Надёжнее хранить такие чеки в базе, но это усложнит хранилище.
- Хранится только последний ожидающий чек пользователя. Если прислать два повтора подряд и нажать кнопку под первым вопросом, сохранится второй чек.
- Строка `items_total_mismatch` фактически стала частью контракта между M2 и M4, но описана только в коде M2. Её стоит перенести в `common/`.
