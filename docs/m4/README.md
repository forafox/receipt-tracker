# M4: ход разработки

Зона ответственности: Telegram-бот (`bot/`), пайплайн (`pipeline/`) и хранилище (`storage/`).

Здесь по итерациям записано, что было сделано в M4 и почему. Итерация — это период, за который накопилась серия моих коммитов.

## Итерация 1. Старт проекта (28–29.09)

Коммиты:

- `docs: add project readme and contributing guidelines`
- `docs: add module overview and architecture diagram`

Сделано:

- README с описанием идеи и CONTRIBUTING с правилами кода, веток и коммитов.
- Разделение системы на модули M1–M4 и схема архитектуры (`docs/architecture.jpg`, `docs/architecture.pdf`).

Почему: до начала разработки нужно было договориться, кто за что отвечает и как модули передают данные друг другу.

## Итерация 2. Бот как отдельный компонент (03.10)

Коммиты:

- `chore: set up uv project with ruff, mypy and pytest`
- `feat(bot): add telegram bot with start, help, month and photo handlers`
- `test(bot): cover start, month and photo handlers`
- `feat(bot): reply in russian or english based on telegram language`
- `test(bot): cover language detection and middleware`
- `docs(bot): describe telegram bot module in readme`

Сделано:

- Бот на aiogram 3: `/start`, `/help`, `/month` и приём фото.
- Бот обращается к остальной системе через интерфейс `ReceiptService`. Остальных модулей ещё не было, поэтому вместо них стояла заглушка с готовым текстом ответа.
- Ответы на русском или английском: язык берётся из `language_code`, который Telegram присылает с каждым сообщением. Тексты собраны в `bot/texts.py`.
- Тесты обработчиков без обращения к Telegram.

Вход: сообщения Telegram (команды, фото). Выход: текст ответа пользователю.

Открытые вопросы:

- Сервис возвращал боту готовую строку. Из-за этого ответы заглушки были только на русском, а бот не мог сам оформить результат.

## Итерация 3. Соединение с M2 и хранилище (11.10)

Коммиты:

- `feat(pipeline): parse receipt photos and reply with store, date and total`
- `feat(storage): save receipts and show monthly spending`

Сделано:

- Пайплайн (`pipeline/receipt.py`) вызывает этапы по очереди: распознавание текста, разбор чека через `extract.parse_receipt` (M2), сохранение.
- Если на чеке нет ни даты, ни суммы, пайплайн выбрасывает `ReceiptUnreadable`, и бот просит переснять фото.
- Хранилище чеков на SQLite (`storage/receipts.py`).
- `/month` считает сумму и число чеков за текущий месяц. Границы месяца берутся в часовом поясе пользователя, а не в UTC.

Было: сервис возвращал боту строку.
Стало: сервис возвращает `Receipt`, а бот сам оформляет ответ на нужном языке.
Почему: оформление ответа относится к боту, а пайплайн должен отдавать данные. Так исчезла проблема с ответами только на русском.

OCR ещё не был готов, поэтому на месте M1 стояла заглушка, и любое фото считалось нераспознанным.

Открытые вопросы:

- В `common/` два разных `Receipt`: один отдаёт M2, другой ждёт M3. Пока их не сведут в один контракт, классификатор нельзя подключить к пайплайну.
- Интерфейс хранилища лежит в `storage/`, хотя по CONTRIBUTING контракты должны быть в `common/`.
- Повторно присланный чек сохранялся и учитывался дважды.

## Итерация 4. Соединение с M1, повторы и история (18.10)

Коммиты:

- `feat(pipeline): recognize receipts with configured ocr engine`
- `feat(bot): accept receipt images sent as files`
- `feat(storage): skip duplicate receipts`
- `feat(bot): add history command with recent receipts`
- `feat(bot): add undo command to delete last receipt`

Сделано:

- Заглушка OCR заменена на `OcrService` из M1, движок выбирается переменной `OCR_ENGINE`. Теперь цепочка фото, текст, чек, сохранение работает целиком.
- Ошибки OCR разделены. Битое изображение считается нераспознанным чеком, и пользователь получает просьбу переснять. Недоступный движок считается сбоем сервера и пишется в лог.
- Чек можно прислать файлом: Telegram его не сжимает, и OCR работает точнее. Пока идёт распознавание, бот показывает статус «печатает…».
- Повторный чек (тот же магазин, дата и сумма) не сохраняется. Существующая база обновляется при запуске без потери данных.
- `/history` показывает последние 5 чеков.
- `/undo` удаляет последний сохранённый чек и показывает, какой именно. Удаляется чек, присланный последним, а не чек с самой поздней датой.

Почему: после появления OCR в M1 можно было впервые собрать весь путь от фото до ответа. Повторы, история и `/undo` нужны, чтобы `/month` показывал правильную сумму: пользователь видит, что именно сохранилось, и может убрать чек, в котором OCR ошибся.

Открытые вопросы:

- Повтор определяется по магазину, дате и сумме. Если OCR прочитает одно из полей по-разному на двух фото одного чека, повтор не найдётся.
- `/undo` удаляет чек целиком. Исправить отдельное поле (например, сумму) пока нельзя, можно только удалить чек и прислать фото заново.
- Распознавание идёт в потоке внутри процесса бота. Непонятно, как это поведёт себя при нескольких пользователях одновременно и не стоит ли вынести OCR в отдельный сервис.
- Подключение классификатора M3 всё ещё ждёт общего контракта `Receipt` и извлечения товаров в M2.
